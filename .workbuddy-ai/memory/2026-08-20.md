# 2026-08-20 — KRPC 长连接并发测试 flake 诊断

## 任务背景
用户要求冻结新功能，把已有能力用「可重复测试」跑透。最终交付：Docker 部署、测试脚本、原始结果、故障日志、1~2 个真实修复。
卡点：`LongConnectionConcurrencyTest.multiplexedChannelHandlesHighConcurrencyWithoutLeak` 在"全模块负载"下偶发 `Connection refused: 127.0.0.1:19999`（监听 socket 中途消失）；隔离运行 100% 绿。

## 关键发现
- krpc-provider 仅两个测试类：`FaultDrillTest`(ZK 不可达→整类 `@BeforeAll` assumeTrue skip) 和 `LongConnectionConcurrencyTest`；krpc-consumer 无 JUnit 测试（仅 main）。→ provider fork 自包含。早先"全模块 vs 隔离"差异来自 **stale-surefire-XML 误判**（`-Dtest` 未带 `-Dsurefire.failIfNoSpecifiedTests=false` 时 reactor 在 krpc-api 失败，provider 未真正重跑，旧 1502 失败 XML 残留）。
- 服务端无任何代码关闭 parent(监听) channel：`NettyServerHandler.exceptionCaught`/`HeartbeatHandler` 只关 child channel；只有 `NettyRpcServer.start()` 的 `finally{shutdown}` 和 `stop()`（`@AfterAll`，测试方法返回后才跑）。
- pom surefire 3.2.5 未显式配 `argLine` → 默认 `${argLine}`，故 `-DargLine` 生效。
- `ServiceProvider.degradeService` 连续 5 次反射失败后降级返 503；本测试 happy-path（方法存在）不触发，非根因。

## 根因（已捕获失败 run 证实）
- 20 次循环第 5 次复现失败，diag 关键行：`[main] stop() called` 时间戳 **早于** `[Thread-1] server BOUND to port 19999` 约 1.7s；断言 `expected:<0> but was:<2000>`（全部 2000 请求失败）。
- 结论：**不是监听 socket 中途崩溃**，而是 `@BeforeAll` 用 `Thread.sleep(600)` 当"服务端就绪"猜测；服务端在自己的线程里 `bind().sync()` 在负载下偶尔 >600ms 才完成 → 测试开火时端口还没在监听 → 全部 `Connection refused`。之前 53/498/1502 的部分成功只是 bind 完成得"晚但没那么晚"。diag 中无 UNCAUGHT / parent closeFuture / exceptionCaught，排除事件循环死亡假设。
- 本质：测试就绪竞态（harness timing bug），非框架崩溃 bug。

## 已落地的真实修复
1. **框架 (RpcServer 接口 + NettyRpcServer 实现)**：新增就绪契约 —— `RpcServer` 接口声明 `awaitStarted(timeout, unit)` 与 `isBound()`；`NettyRpcServer` 用 `CountDownLatch startedLatch`（`bind().sync()` 成功后 countDown）实现。调用方不再靠魔术数字 sleep 猜测就绪。已**同步还原**此前注入的文件诊断代码（diag/diagFactory/exceptionCaught 监听全部移除）。
   - 注意：测试里 `server` 变量类型是 `RpcServer` 接口，故必须在接口声明这两个方法，否则测试编译失败（`找不到符号 awaitStarted`）。
2. **测试 (LongConnectionConcurrencyTest)**：`@BeforeAll` 用 `assertTrue(server.awaitStarted(15, SECONDS), ...)` 替换 `Thread.sleep(600)`。确定性就绪等待。
