# KRPC 秋招面试说明

## 1. 一分钟项目介绍

KRPC 是一个基于 Netty 实现的轻量级 Java RPC 框架。项目通过自定义应用层协议完成请求和响应传输，使用长连接复用以及 `requestId + CompletableFuture` 支持同一连接上的并发请求；使用 ZooKeeper 完成服务注册、发现和节点变更感知，并实现一致性哈希、重试、熔断、限流和链路追踪。

我后续优化的重点不是继续堆组件，而是研究框架在高并发和故障场景下是否可靠。例如：并发建连是否存在锁竞争、请求超时后是否残留 Future、异常协议帧是否会造成大内存分配，以及重试、节点摘除和熔断之间应如何协作。

## 2. 最值得讲的三个难点

### 2.1 单连接多路复用与请求关联

问题：多个线程通过同一个 Netty Channel 并发发送请求后，响应返回顺序不一定与请求发送顺序一致，不能依靠线程或顺序匹配响应。

方案：客户端为每次调用生成唯一 `requestId`，把 `CompletableFuture<RpcResponse>` 放入并发 Map。响应到达后，Handler 根据 `requestId` 找到 Future 并完成它，调用线程再取得自己的响应。

需要主动说明的边界：请求超时、写失败和线程中断时都必须删除 Map 中的条目；迟到响应找不到 Future 时只能丢弃并记录日志，否则长期运行会产生内存泄漏。

### 2.2 长连接缓存的并发建连

原始问题：连接缓存使用一个全局对象加锁，而且在锁内同步等待 TCP 建连。某个节点网络异常时，其他线程即使连接不同节点，也会被同一把锁阻塞。

优化方案：先无锁读取可用 Channel；缓存未命中时使用“服务地址对应的锁”执行二次检查和建连，使相同地址只创建一条连接，不同地址可以并行建连。同时增加连接超时、TCP KeepAlive 和 `TCP_NODELAY`，并在 Channel 关闭后删除失效缓存。

方案取舍：当前每个访问过的地址会保留一个小型锁对象。这对服务节点数量有限的 RPC 客户端可以接受；如果需要支持大量临时地址，可以进一步改为缓存异步 `ChannelFuture` 或使用 Netty `ChannelPool`，同时设计锁对象回收策略。

### 2.3 半包处理与协议安全

问题：TCP 是字节流，消息可能发生半包和粘包；此外，解码器不能直接相信远端传来的长度字段，否则异常客户端可以声明超大长度，诱导服务端分配大数组。

方案：协议包含魔数、版本、Trace 长度、消息类型、序列化类型和消息体长度。解码时使用 reader index 回滚处理半包，并在创建字节数组前校验负数和最大长度。发送端同样校验长度，防止本机生成不符合协议约束的帧。

测试发现：原解码器必须收到完整的最小帧头后才检查 Trace 长度。优化后只要收到固定的 7 字节前缀，就可以尽早拒绝异常长度，减少无效连接占用。

## 3. 技术选型怎么解释

### 为什么选择 Netty，而不是直接使用 Socket

Java 原生 Socket 适合验证基本调用流程，但连接管理、事件循环、半包处理和高并发 I/O 都需要自己维护。Netty 提供成熟的 Reactor 线程模型、Pipeline、ByteBuf 和异步 Channel API，使项目可以把精力放在 RPC 协议、调用关联和服务治理上。

### 为什么不用 Dubbo 或 gRPC

这个项目的目标不是替代成熟框架，而是理解 RPC 的核心机制，并通过自己实现发现工程问题。Dubbo 更适合直接落地完整的 Java 微服务治理；gRPC 在跨语言、IDL 和 HTTP/2 场景更有优势。KRPC 选择自定义协议，是为了能够解释消息边界、序列化、连接复用和请求关联，但生产环境会优先评估成熟框架。

### 为什么选择 ZooKeeper

RPC 服务节点需要临时节点、会话失效感知和节点变更通知。ZooKeeper 的临时节点和 Watcher 与这个模型匹配，同时具备明确的一致性语义。代价是运维和会话管理更复杂；如果业务更关注配置管理、控制台和云原生体验，可以考虑 Nacos，如果强调轻量和 watch API，可以评估 etcd。

### 为什么使用 CompletableFuture

Netty 写操作是异步的，而当前代理接口对调用方表现为同步方法。Future 可以把异步响应事件与同步等待桥接起来，也为以后提供异步 RPC API 保留扩展空间。关键不在于使用 Future 本身，而在于完整管理注册、完成、失败、超时和清理的生命周期。

### 为什么选择一致性哈希

一致性哈希适合希望相同请求键稳定路由到相同节点的场景，节点变化时只迁移部分键。虚拟节点用于缓解物理节点较少导致的数据倾斜。它不适合所有 RPC：无状态接口使用最少活跃数或基于延迟的负载均衡通常更直接，因此框架仍保留随机和轮询等策略。

## 4. 故障治理如何回答

可以按以下顺序解释一次调用：

1. 服务发现获得候选节点，过滤临时不可用节点，再执行负载均衡。
2. 客户端复用已有 Channel；没有连接时按地址并发安全地创建连接。
3. 请求写入后等待对应 Future，写失败或超时会清理 Pending 请求并临时摘除节点。
4. 对允许重试的服务执行有限次数重试，下一次发现会避开已经摘除的节点。
5. 方法级熔断器统计最终调用结果，达到阈值后快速失败，经过恢复窗口后进入半开状态探测。
6. 后台探测任务发现节点恢复后，将节点重新加入负载均衡集合。

不要回避当前不足：重试白名单目前按服务粒度配置，还不能严格表达某一个方法是否幂等。下一步应增加方法级幂等标记、指数退避和随机抖动，禁止写操作被无条件重试。

## 5. 高频追问

### 为什么超时后要摘除节点，一次超时会不会误判

当前策略偏向快速故障转移：只有连接、写入和响应超时等传输故障会摘除节点，普通业务失败不会直接摘除；后台探测会重新加入恢复节点。它的代价是偶发慢请求可能造成短暂误摘除。进一步优化可以引入连续失败阈值、滑动窗口和被动统计，把网络不可达与单次慢请求分开处理。

### 为什么熔断器按方法，而节点摘除按地址

两者解决的问题不同。节点摘除处理单个实例的网络或进程故障，避免重试继续命中故障实例；方法级熔断处理某项服务能力的持续失败，即使其他节点仍在线，也可以通过快速失败保护调用方线程和下游系统。

### 为什么不直接使用 LengthFieldBasedFrameDecoder

当前协议的消息体长度字段位于可变长度 Trace 字段之后，偏移量不固定，因此使用自定义解码器更直观。这个设计也暴露了协议版本演进问题：下一版可以把“总帧长度”放在固定前缀中，再复用 Netty 的长度字段解码器，减少手写状态机和安全边界。

### 如何证明优化有效

不能只展示功能。应固定机器、JDK、消息大小和并发度，分别记录修改前后的吞吐量、P95/P99 延迟、连接数、Pending Map 峰值和故障恢复时间；再模拟节点端口不可达、服务端延迟、返回异常帧和运行中宕机。没有实际压测前，不在简历中填写提升百分比。

## 6. 简历表述模板

项目名称：KRPC - 基于 Netty 的轻量级高可用 RPC 框架

- 基于自定义二进制协议与 Netty 长连接实现 RPC 通信，通过 `requestId + CompletableFuture` 完成单连接并发请求的响应关联，并完善超时、写失败和迟到响应的生命周期清理。
- 设计按服务地址隔离的并发建连机制，消除慢节点建连对其他节点的全局阻塞；增加连接超时、失效 Channel 移除和 TCP 参数配置。
- 基于 ZooKeeper 临时节点和 Watcher 实现服务注册发现及动态节点感知，结合一致性哈希、故障节点摘除、重试、方法级熔断和后台恢复探测完成客户端容错。
- 为协议增加魔数、版本、消息类型和序列化类型校验，并限制 Trace 与消息体长度；通过 EmbeddedChannel 覆盖超长帧和半包边界测试。

完成压测后再增加一条量化结果，例如：在固定消息大小和并发度下，长连接复用相较于逐请求建连将吞吐量从 `[A]` 提升至 `[B]`，P99 从 `[C] ms` 降至 `[D] ms`。

## 7. 下一阶段优先级

1. 方法级幂等重试、指数退避和随机抖动。
2. 区分连接失败、请求超时和业务异常，使用滑动窗口计算节点健康度。
3. 将请求超时、连接超时、ZooKeeper 地址和协议长度上限外部配置化。
4. 增加 P50/P95/P99、成功率、重试次数、熔断次数和 Pending 请求数指标。
5. 使用故障注入脚本复现节点宕机、慢响应和注册中心短暂不可用。
