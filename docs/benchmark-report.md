# KRPC 本地基准测试报告

## 测试目标

比较以下两种客户端连接策略：

- 逐请求建连：每次 RPC 调用建立并关闭一个 TCP 连接。
- 单连接多路复用：复用一个 Netty Channel，通过 `requestId + CompletableFuture` 关联并发响应。

本测试用于验证连接复用优化，不代表跨机器或生产环境容量。

## 测试环境

- 日期：2026-07-19
- CPU：12th Gen Intel Core i5-12500H，12 核 16 线程
- JDK：Java 17.0.12 HotSpot 64-Bit
- 网络：客户端和服务端运行在同一台 Windows 主机，通过 `127.0.0.1:9999` 通信
- 序列化：Hessian
- 请求：`UserService.getUserByUserId(Integer)`
- 响应：固定的小型 `User` 对象

基准服务端不连接 ZooKeeper，并关闭限流、Zipkin 上报和业务日志，避免外部依赖与逐请求日志污染结果。每轮正式测试前执行 500 次预热，正式发送 5000 次请求。

## 单轮结果

| 并发度 | 连接策略 | 成功率 | QPS | P50 | P95 | P99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 20 | 逐请求建连 | 100% | 2082.37 | 8.238 ms | 20.111 ms | 29.962 ms |
| 20 | 单连接多路复用 | 100% | 4746.63 | 4.076 ms | 5.282 ms | 6.993 ms |
| 100 | 逐请求建连 | 100% | 1996.50 | 49.635 ms | 59.060 ms | 67.039 ms |
| 100 | 单连接多路复用 | 100% | 5640.96 | 17.629 ms | 21.864 ms | 25.185 ms |

在该单轮本机样本中，单连接多路复用相对逐请求建连的吞吐量分别提高 127.94% 和 182.54%。该百分比需要在固定 CPU 频率、重复多轮并统计均值和方差后，才适合写入简历。

## 运行中发现的问题

第一次运行的成功率为 0。服务端日志显示反射调用抛出 `IllegalAccessException`：基准服务实现是私有内部类，即使方法是 public，其他包的 Handler 也不能访问其宿主类。将实现类改为 public 后，单请求验证和两轮正式测试均达到 100% 成功。

## 下一步

1. 每个并发度至少重复 5 轮，记录均值、标准差和进程 CPU/GC。
2. 增加 1 KB、10 KB 和 100 KB 响应，验证序列化与内存复制成本。
3. 增加多 Channel 连接池，与单 Channel 比较吞吐和尾延迟。
4. 注入服务端延迟、连接中断和节点宕机，记录超时、重试与恢复时间。
5. 将客户端和服务端部署到两台机器，补充真实网络 RTT 下的结果。

## EventLoop 慢调用隔离 A/B 测试

### 测试方法

- 日期：2026-09-05
- 调用链：真实 `RpcClient -> TCP -> Netty 编解码 -> 服务端反射调用 -> RpcResponse`
- 请求总量：120，并发度：48
- 混合负载：每 6 个请求包含 1 个 `Thread.sleep(100 ms)` 的阻塞调用，其余为无等待快调用
- A 组：业务方法直接运行在 Channel 所属 EventLoop，复现改造前实现
- B 组：业务方法投递到 8 线程、256 队列容量的有界业务线程池
- 统计口径：整体 QPS，以及仅快请求的 P95/P99；每组先执行 20 次快请求预热

`Thread.sleep` 不消耗 CPU，但会占住执行线程，可稳定模拟 JDBC 查询、文件 I/O、下游 HTTP/RPC 等同步阻塞等待。

### 单轮结果

| 执行模型 | 成功率 | QPS | 快请求 P95 | 快请求 P99 | 总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| EventLoop 直接执行 | 100% | 54.8 | 875.98 ms | 976.71 ms | 2190.68 ms |
| 有界业务线程池 | 100% | 359.1 | 113.60 ms | 115.16 ms | 334.17 ms |

该轮测试中，业务线程隔离使混合负载吞吐达到原来的 6.56 倍，快请求 P95 下降 87.0%。慢请求自身仍需等待约 100 ms；收益来自慢调用可并行执行，且不再阻塞 EventLoop 读取、解码和分发后续快请求。

### 结论与边界

该结果验证的是慢调用下的故障隔离效果，不是项目的生产容量。测试使用本机回环网络、固定休眠和单轮样本；简历可描述“在本机可控混合负载实验中”，不应直接外推线上 QPS。正式结果建议重复至少 5 轮并报告均值、标准差、CPU、GC 和拒绝率。

本项目使用自定义二进制 RPC 协议，Java 基准程序可以直接标记快慢请求并统计各自分位数，因此比 JMeter 更适合本次机制验证。JMeter 仍可通过 Java Request Sampler 接入，适合后续做长时间稳定性、阶梯加压和容量拐点测试。

运行命令：

```bash
mvn -q -pl krpc-provider -am "-Dtest=EventLoopIsolationBenchmarkTest" "-Dsurefire.failIfNoSpecifiedTests=false" test
```
